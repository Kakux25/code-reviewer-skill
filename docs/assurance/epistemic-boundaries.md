# Reviewer Boundaries

All specialists must separate observations, inferences, judgments under versioned criteria, and recommendations. A plausible narrative cannot satisfy an evidence requirement. Every confirmed finding needs a trigger, expected invariant, concrete consequence, evidence and an attempted refutation that survives examination.

| Reviewer | Required evidence | Method and output | Falsification | Cannot conclude |
| --- | --- | --- | --- | --- |
| code-reviewer | Base/candidate, task contract, relevant callers and checks | Trigger-to-consequence analysis; findings and checks | Find guards, counterexamples and pre-existing behavior; run focused reproduction when justified | Global architectural adequacy, system safety, authorship |
| architecture-reviewer | Base-derived concerns, views, ADRs, boundaries and quality scenarios | Repository rubric; scenario risks, sensitivity and tradeoff points; complexity separate from quality | Test alternative mechanisms against the same invariant; inspect consumers outside diff | Folder layout proves architecture; undocumented deployment decisions are known |
| system-dynamics-reviewer | Variables with units, operating range, queues/resources, timing and traces or documented models | Causal links with polarity/delay; stocks, flows, feedback and behavior over time | Counter-scenarios, missing confounders, dimensional checks, trace comparison and parameter sensitivity | A generated diagram proves causality; an uncalibrated simulation predicts production |
| safety-stpa-reviewer | Unacceptable losses, system boundary, hazards, controllers, actions, feedback and process models | Loss → hazard → control structure → unsafe control action → causal scenario → constraint | Examine omitted/incorrect actions, timing/order, duration and contexts that invalidate a scenario | No code bug means safe; every constraint is formally verified |
| incident-memory | Source incident, mechanism, state, intervention, outcome and applicability conditions | Retrieve → adapt → revise → retain only with authorization; applicable/rejected/uncertain analogues | Seek disanalogies, incompatible conditions and intervention side effects | Similar wording proves applicability; no match means no historical risk |
| sociotechnical-reviewer | Technical coordination graph and dated ownership/review/runbook evidence | Compare required coordination edges with observable responsibility and handoff paths | Check stale ownership, aliases, alternate routing and confirmed handoff evidence | Missing CODEOWNERS proves nobody owns it; culture, competence or motives |
| final-engineering-judge | Scope, specialist envelopes, raw evidence, claims, warrants and defeaters | Assemble and challenge the assurance case; scoped recommendation | Investigate what could falsify each major positive claim | Majority vote proves truth; a recommendation authorizes deployment |

Incomplete input produces an explicit uncertainty or abstention. `Not applicable` requires a scope-based rationale and evidence; it must not hide an unperformed review. Freeze required reviewer coverage before candidate judgment. Candidate exposure is recorded, not erased by opening another prompt.

Documented project principles remain a distinct check. Preserve the existing `Unverifiable` outcome when no principles are documented. Do not infer an organization's values or personality from code. In composed operation, architecture-reviewer owns architectural principles; code-reviewer may report concrete local violations without double-counting them.
